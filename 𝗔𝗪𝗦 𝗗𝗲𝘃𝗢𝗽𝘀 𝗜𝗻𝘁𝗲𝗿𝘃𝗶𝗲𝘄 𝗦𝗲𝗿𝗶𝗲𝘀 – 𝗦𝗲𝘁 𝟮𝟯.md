# 2. What is Branching Strategy in Git? Which Git Branching Strategy Are You Using?

## What is Git Branching Strategy?

A **Git branching strategy** is a defined approach for creating, managing, and merging branches in a Git repository.

It helps the development and DevOps teams to:

- Isolate feature development
- Manage multiple developers working in parallel
- Perform code reviews
- Maintain stable production code
- Manage releases
- Handle production issues
- Support CI/CD pipelines
- Reduce conflicts between developers

## Which Git Branching Strategy Are You Using?

In my projects, I have mainly used a **feature-based branching strategy** with separate `feature`, `develop`, `release`, `main`, and `hotfix` branches.

The typical flow is:

```text
feature/* → develop → release/* → main
                                  ↓
                              Production
```

## Branches Used

### 1. Main Branch

The `main` branch contains **production-ready code**.

```text
main
└── Production-ready code
```

Production deployments are triggered from the `main` branch after successful testing and approval.

### 2. Develop Branch

The `develop` branch is used as an **integration branch**.

Completed feature branches are merged into `develop` for integration testing.

```text
develop
└── Integration branch
```

### 3. Feature Branch

Developers create feature branches for individual features or changes.

```text
feature/*
└── Individual feature development
```

Examples:

```text
feature/login
feature/payment
feature/user-profile
```

Feature branches are normally created from `develop`.

### 4. Release Branch

A release branch is created when the changes are ready for final testing and release preparation.

```text
release/*
└── Release preparation and testing
```

Examples:

```text
release/v1.0.0
release/v1.2.0
```

The release branch is used for:

* QA testing
* UAT
* Bug fixing
* Final validation
* Release preparation

### 5. Hotfix Branch

A hotfix branch is created from `main` when there is a critical production issue.

```text
hotfix/*
└── Critical production fixes
```

Examples:

```text
hotfix/payment-failure
hotfix/login-issue
```

After fixing and testing, the hotfix is merged into both `main` and `develop`.

---

## Example Workflow

### Step 1: Create a Feature Branch

First, switch to the `develop` branch and get the latest changes.

```bash
git checkout develop
git pull origin develop
```

Create a feature branch:

```bash
git checkout -b feature/login
```

### Step 2: Commit and Push Changes

After completing the development:

```bash
git add .
git commit -m "Added login feature"
git push origin feature/login
```

### Step 3: Create a Pull Request

Create a Pull Request:

```text
feature/login → develop
```

The Pull Request goes through:

* Code review
* CI/CD checks
* Unit testing
* Code quality checks
* Security scanning

After approval, the feature branch is merged into `develop`.

### Step 4: Create a Release Branch

When the application is ready for release:

```bash
git checkout develop
git pull origin develop
git checkout -b release/v1.2.0
```

The release branch is tested by the QA/UAT teams.

### Step 5: Merge Release into Main

After successful testing and approval:

```text
release/v1.2.0 → main
```

The `main` branch now contains production-ready code.

The production CI/CD pipeline can deploy the application to production.

---

## Hotfix Workflow

For a critical production issue:

```text
main
  |
  v
hotfix/payment-fix
  |          |
  v          v
main      develop
```

Create the hotfix branch:

```bash
git checkout main
git pull origin main
git checkout -b hotfix/payment-fix
```

After fixing the issue:

```bash
git add .
git commit -m "Fixed payment issue"
git push origin hotfix/payment-fix
```

After approval, merge the hotfix into:

```text
hotfix/payment-fix → main
```

and also:

```text
hotfix/payment-fix → develop
```

This ensures the production fix is also available in the development branch.

---

## Complete Branching Strategy

```text
                         feature/*
                            |
                            v
                         develop
                            |
                            v
                       release/*
                            |
                            v
                           main
                            |
                            v
                        Production
```

### Hotfix

```text
                           main
                            |
                            v
                         hotfix/*
                          /    \
                         v      v
                       main   develop
```

# 3. Explain What Kinds of Conflicts You Get and How You Resolve Them?

## What is a Git Conflict?

A **Git conflict** occurs when Git cannot automatically merge changes from two different branches.

Usually, conflicts happen when two developers modify the **same file or the same lines of code** differently.

Git commonly reports conflicts during:

- `git merge`
- `git rebase`
- `git cherry-pick`
- Pull Request (PR) merging

---

## Types of Git Conflicts

### 1. Same Line Conflict

This is the most common type.

For example, developer A changes:

```text
version: 1.0
```

to:

```text
version: 1.1
```

Developer B changes the same line to:

```text
version: 2.0
```

Git does not know which change should be retained.

Git marks the conflict like this:

```text
<<<<<<< HEAD
version: 1.1
=======
version: 2.0
>>>>>>> feature-branch
```

We need to manually decide which version should be used.

---

### 2. Same File / Overlapping Changes

Two developers modify different but overlapping sections of the same file.

Example:

```text
Developer A → application.yaml
Developer B → application.yaml
```

If the changes overlap, Git may generate a conflict.

---

### 3. Add/Add Conflict

Two branches create a file with the **same filename**, but with different content.

Example:

```text
Branch A → creates config.yaml
Branch B → creates config.yaml
```

Git cannot automatically decide which file should be kept.

---

### 4. Modify/Delete Conflict

One branch modifies a file while another branch deletes the same file.

Example:

```text
Branch A → modifies application.yaml
Branch B → deletes application.yaml
```

Git needs us to decide whether the file should be retained or deleted.

---

### 5. Delete/Delete Conflict

Both branches delete the same file, but Git may need to determine the resulting state depending on the history and merge operation.

---

# How Do You Resolve a Merge Conflict?

Let's take an example:

```text
develop
   |
   └── feature/login
```

I am working on `feature/login`, and the `develop` branch has changes that conflict with my branch.

## Step 1 — Switch to the Feature Branch

```bash
git checkout feature/login
```

---

## Step 2 — Get the Latest Changes

```bash
git fetch origin
```

Or:

```bash
git pull origin develop
```

---

## Step 3 — Merge Develop Into Feature Branch

```bash
git merge develop
```

If there is a conflict, Git will show something like:

```text
CONFLICT (content): Merge conflict in application.yaml
Automatic merge failed; fix conflicts and then commit the result.
```

---

## Step 4 — Check the Conflicted Files

```bash
git status
```

Example:

```text
both modified:   application.yaml
```

---

## Step 5 — Open the Conflicted File

Git adds conflict markers:

```text
<<<<<<< HEAD
replicas: 3
=======
replicas: 5
>>>>>>> develop
```

The meaning is:

```text
<<<<<<< HEAD
Your current branch changes
=======
Changes from the branch being merged
>>>>>>> develop
```

---

## Step 6 — Resolve the Conflict

We manually decide which change should be retained.

For example:

```yaml
replicas: 5
```

Then remove the conflict markers:

```text
<<<<<<<
=======
>>>>>>>
```

The final file should contain only the valid configuration.

---

## Step 7 — Stage the Resolved File

```bash
git add application.yaml
```

Or all resolved files:

```bash
git add .
```

---

## Step 8 — Commit the Resolution

```bash
git commit -m "Resolved merge conflict"
```

---

## Step 9 — Push the Changes

```bash
git push origin feature/login
```

---

# How I Handle Conflicts During Rebase

If I am using rebase:

```bash
git checkout feature/login
git rebase develop
```

If a conflict occurs:

```bash
git status
```

I resolve the conflicted file manually and then:

```bash
git add .
git rebase --continue
```

If there are additional conflicts, I repeat the same process.

After the rebase is completed:

```bash
git push --force-with-lease origin feature/login
```

I prefer `--force-with-lease` instead of `--force` because it provides an additional safety check.

---

# How to Abort a Conflict Resolution

If I realize that the merge should not continue:

```bash
git merge --abort
```

For a rebase:

```bash
git rebase --abort
```

This returns the branch to the state before the operation started.

---

# My Practical Approach to Conflict Resolution

In a real project, I follow these steps:

```text
1. Check the conflicted files
        ↓
2. Understand both changes
        ↓
3. Discuss with the developer if required
        ↓
4. Resolve the conflict manually
        ↓
5. Remove Git conflict markers
        ↓
6. git add
        ↓
7. Commit / rebase --continue
        ↓
8. Run unit tests
        ↓
9. Run CI/CD pipeline
        ↓
10. Push the changes
```

I don't blindly choose **ours** or **theirs**. I first understand why both changes were made and then keep the correct business and technical logic.

# Interview Answer

> **Git conflicts usually occur when Git cannot automatically merge changes from two branches. The most common conflict is when two developers modify the same line or overlapping sections of the same file. We can also get conflicts such as add/add, modify/delete, and delete/delete.**
>
> **When I get a conflict, I first run `git status` to identify the conflicted files. Then I open the files, review both changes using the conflict markers, and decide the correct change. After resolving the conflict, I remove the conflict markers, run `git add`, and complete the merge with `git commit`. If I'm doing a rebase, I use `git rebase --continue`. Finally, I run tests and push the changes.**
>
> **If the conflict is unclear or involves business logic, I discuss it with the developer who made the change rather than blindly selecting one side.**
