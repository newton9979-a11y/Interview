# 2. What is Branching Strategy in Git? Which Git Branching Strategy Are You Using?

## What is Git Branching Strategy?

A **Git branching strategy** is a defined approach for creating, managing, and merging branches in a Git repository.

It helps the development and DevOps teams to:

- Isolate feature development
- Manage multiple developers working in parallel
- Perform code reviews
- Maintain stable production code
- Manage releases
- Handle production issues
- Support CI/CD pipelines
- Reduce conflicts between developers

## Which Git Branching Strategy Are You Using?

In my projects, I have mainly used a **feature-based branching strategy** with separate `feature`, `develop`, `release`, `main`, and `hotfix` branches.

The typical flow is:

```text
feature/* → develop → release/* → main
                                  ↓
                              Production
```

## Branches Used

### 1. Main Branch

The `main` branch contains **production-ready code**.

```text
main
└── Production-ready code
```

Production deployments are triggered from the `main` branch after successful testing and approval.

### 2. Develop Branch

The `develop` branch is used as an **integration branch**.

Completed feature branches are merged into `develop` for integration testing.

```text
develop
└── Integration branch
```

### 3. Feature Branch

Developers create feature branches for individual features or changes.

```text
feature/*
└── Individual feature development
```

Examples:

```text
feature/login
feature/payment
feature/user-profile
```

Feature branches are normally created from `develop`.

### 4. Release Branch

A release branch is created when the changes are ready for final testing and release preparation.

```text
release/*
└── Release preparation and testing
```

Examples:

```text
release/v1.0.0
release/v1.2.0
```

The release branch is used for:

* QA testing
* UAT
* Bug fixing
* Final validation
* Release preparation

### 5. Hotfix Branch

A hotfix branch is created from `main` when there is a critical production issue.

```text
hotfix/*
└── Critical production fixes
```

Examples:

```text
hotfix/payment-failure
hotfix/login-issue
```

After fixing and testing, the hotfix is merged into both `main` and `develop`.

---

## Example Workflow

### Step 1: Create a Feature Branch

First, switch to the `develop` branch and get the latest changes.

```bash
git checkout develop
git pull origin develop
```

Create a feature branch:

```bash
git checkout -b feature/login
```

### Step 2: Commit and Push Changes

After completing the development:

```bash
git add .
git commit -m "Added login feature"
git push origin feature/login
```

### Step 3: Create a Pull Request

Create a Pull Request:

```text
feature/login → develop
```

The Pull Request goes through:

* Code review
* CI/CD checks
* Unit testing
* Code quality checks
* Security scanning

After approval, the feature branch is merged into `develop`.

### Step 4: Create a Release Branch

When the application is ready for release:

```bash
git checkout develop
git pull origin develop
git checkout -b release/v1.2.0
```

The release branch is tested by the QA/UAT teams.

### Step 5: Merge Release into Main

After successful testing and approval:

```text
release/v1.2.0 → main
```

The `main` branch now contains production-ready code.

The production CI/CD pipeline can deploy the application to production.

---

## Hotfix Workflow

For a critical production issue:

```text
main
  |
  v
hotfix/payment-fix
  |          |
  v          v
main      develop
```

Create the hotfix branch:

```bash
git checkout main
git pull origin main
git checkout -b hotfix/payment-fix
```

After fixing the issue:

```bash
git add .
git commit -m "Fixed payment issue"
git push origin hotfix/payment-fix
```

After approval, merge the hotfix into:

```text
hotfix/payment-fix → main
```

and also:

```text
hotfix/payment-fix → develop
```

This ensures the production fix is also available in the development branch.

# 3. Explain What Kinds of Conflicts You Get and How Do You Resolve Them?

## What is a Git Conflict?

A **Git conflict** occurs when Git cannot automatically merge changes from two branches because the changes affect the same part of a file or there are conflicting changes between branches.

Conflicts commonly occur during:

- `git merge`
- `git rebase`
- Pull Request merges
- Cherry-picking commits

---

## What Kinds of Conflicts Do You Get?

### 1. Same Line Conflict

This is the most common type of conflict.

For example, two developers modify the same line differently.

**Developer A:**

```text
database_url = "mysql://db-prod"
```

Developer B:

database_url = "mysql://db-dev"

Git cannot decide which change should be kept.

2. Same File, Different Changes

Two developers modify different sections of the same file.

Sometimes Git can automatically merge these changes, but if the changes overlap or the context is ambiguous, Git may generate a conflict.

3. Add/Add Conflict

Two developers create a file with the same name and path, but with different contents.

Example:

Developer A → config.yaml
Developer B → config.yaml

Git cannot automatically determine which version should be used.

4. Modify/Delete Conflict

One developer modifies a file while another developer deletes the same file.

Example:

Developer A → Modified application.yaml
Developer B → Deleted application.yaml

Git needs a decision about whether the file should remain or be deleted.

5. Delete/Delete Conflict

Two developers delete the same file differently or from different branches.

Git may require manual resolution depending on the merge history.

How Do You Resolve Git Conflicts?

Suppose I am working on:

feature/login

and I want to merge the latest develop changes.

First, I update my local develop branch:

git checkout develop
git pull origin develop

Then switch back to my feature branch:

git checkout feature/login

I can merge develop into my feature branch:

git merge develop

If there is a conflict, Git shows something like:

CONFLICT (content): Merge conflict in application.yaml
Automatic merge failed; fix conflicts and then commit the result.
Step 1: Check the Conflicted Files

I check the status:

git status

Example:

both modified: application.yaml
Step 2: Open the Conflicted File

Git adds conflict markers to the file:

<<<<<<< HEAD
database_url: mysql://dev-db
=======
database_url: mysql://qa-db
>>>>>>> develop

The sections mean:

<<<<<<< HEAD
My current branch changes
======= 
Changes coming from develop
>>>>>>> develop
Step 3: Resolve the Conflict

I discuss with the developer or team if required and decide which change should be retained.

For example:

database_url: mysql://qa-db

I remove the Git conflict markers:

<<<<<<<
=======
>>>>>>>

The final file should contain only the correct configuration.

Step 4: Add the Resolved File

After resolving the conflict:

git add application.yaml

Check the status:

git status
Step 5: Complete the Merge

For a normal merge:

git commit -m "Resolved merge conflict"

Then push the changes:

git push origin feature/login
Conflict Resolution Using Rebase

If I am using rebase and encounter a conflict:

git rebase develop

Git may report a conflict.

I check the conflicted files:

git status

Resolve the files manually and then:

git add .
git rebase --continue

If there are additional conflicts, I repeat the same process.

After the rebase is completed:

git push --force-with-lease origin feature/login

I prefer --force-with-lease instead of --force because it provides an additional safety check before updating the remote branch.

If I Want to Cancel the Operation
Cancel Merge
git merge --abort
Cancel Rebase
git rebase --abort

These commands return the branch to the state before the merge or rebase operation.

How I Handle Conflicts in a DevOps Environment

In a team environment, I follow these practices:

Keep branches updated regularly.
Pull the latest changes before starting development.
Create small and focused commits.
Avoid making unnecessary changes to common files.
Raise Pull Requests for code review.
Use CI/CD checks to validate the changes.
Resolve conflicts carefully instead of blindly choosing one side.
Test the application after resolving conflicts.
Push the resolved changes and allow the CI/CD pipeline to validate them.
Example Scenario

Suppose:

develop
   |
   +------ application.yaml
   |
   |
feature/payment
   |
   +------ application.yaml

Both branches modified the same configuration:

develop:
database: qa-db

feature/payment:
database: payment-db

When I run:

git checkout feature/payment
git merge develop

Git may generate:

<<<<<<< HEAD
database: payment-db
=======
database: qa-db
>>>>>>> develop

I review the changes and determine the correct value.

After resolving:

database: qa-db

Then:

git add application.yaml
git commit -m "Resolved merge conflict in application configuration"
git push origin feature/payment
Interview Answer

"Git conflicts occur when Git cannot automatically merge changes from two branches. The most common conflict is when two developers modify the same line or same section of a file. Other conflicts include add/add, modify/delete, and delete/delete conflicts.

When I get a conflict, I first run git status to identify the conflicted files. I open the files and check the Git conflict markers like <<<<<<<, =======, and >>>>>>>. I review both changes, discuss with the concerned developer if necessary, and keep the correct changes. Then I remove the conflict markers, run git add, and complete the merge using git commit. After that, I run tests and push the changes so that the CI/CD pipeline can validate them.

If the conflict happens during rebase, I resolve the files, run git add, and use git rebase --continue. If required, I can cancel the operation using git merge --abort or git rebase --abort."
